# 09 — 장소 정보 시트, "79%는 어떻게 나왔나" 보이기, 큰 숫자 잘림, 로고

너는 `tripfit/` 폴더에서 일한다. 사용자가 데모를 보고 여섯 가지를 요청했다. 먼저 `web/index.html`(1·2단계 함수, 일정 블록·지도 마커 렌더, 시트 컴포넌트, `renderChecklist`, 엔진 `log`), `solver/demo_builder.py`(`stop_json`, places 직렬화), `solver/sample_seongsu.py`(`PLACE_FACTS`, `place_quality`), `codex/07_mobile.result.md`, `codex/06_try_backend.result.md`를 읽어라.

## 1. 큰 숫자 잘림 (1단계 "6곳 이하로 가능한 방문 순서")

`#fnN`이 76px 고정이라 `2,428,805가지`의 "가지"가 블록 밖으로 잘린다. 숫자 자릿수와 상관없이 블록 안에 들어가게: 최종 문자열 기준으로 폰트 크기를 정하거나(`.fn-n.long`), 렌더 후 `scrollWidth > clientWidth`면 비율로 줄여라. 데스크톱·모바일 둘 다. 오도미터 애니메이션은 유지. 같은 문제가 다른 큰 숫자(만족도 79 : 83, 결제 70,000, 솔버 ms)에도 생길 수 있으니 한 함수(`fitNumber(el)`)로 공통 처리.

## 2. "둘 다 79% 넘게 만족하는 일정" — 계산 근거를 흐름 안에서 보이기

지금 2단계는 제목(둘 다 79% 넘게), 큰 숫자 79 : 83, 체크리스트 막대(항목별 %)를 보여 주지만, **79가 어디서 나왔는지**(가중평균)와 **왜 이 일정이 "균형"인지**(둘 중 낮은 쪽이 가장 높은 일정)가 안 보인다. 발표에서 말로 설명하지 않아도 화면만 보고 이해되게:
- 체크리스트 각 행에 강도 표시를 작은 알약으로: strong "꼭", normal "보통", weak "살짝" (weight 1.0 / 0.7 / 0.4). 행 오른쪽 %는 충족률.
- 사람 블록 상단 % 옆이나 아래 한 줄 식: 예 지민 `(100×1.0 + 50×0.7) ÷ (1.0+0.7) = 79%`. 숫자는 `checklist`(label, weight, fulfilled)에서 계산해 그리고, 그 결과가 `sat`과 소수 첫째 자리까지 맞는지 확인(안 맞으면 `sat`을 쓰고 콘솔 경고). 처음엔 접혀 있고 사람 블록(또는 큰 % 숫자)을 탭하면 펼쳐지는 방식, 자동재생(`_run`)에서는 2단계에서 지민 블록을 한 번 펼쳤다 접는다.
- 저울 블록에 한 줄: "균형 = 덜 만족한 사람의 %가 가장 높은 일정" 과 제목의 79가 `min(지민, 서연)`임을 드러내는 표시(예: 79 숫자 아래 작은 "둘 중 낮은 쪽"). 저울을 밀면 두 숫자와 식이 함께 바뀐다.
- 엔진 로그에 `만족도 = Σ(강도×충족률)/Σ강도 · 지민 79.4 / 서연 83.1` 한 줄.
- `CAPS[2]`(발표 캡션)는 그대로 두되 숫자는 지금처럼 데이터 기반.

## 3. 장소를 누르면 POI 정보 시트

일정 블록(2·3·5단계의 각 stop 카드)과 지도 마커를 누르면 바텀시트(기존 시트 컴포넌트 재사용)로 그 장소 정보를 보여 준다. 4단계 합의 화면의 아이콘도 가능하면.
- 내용: 이름, 카테고리 알약, 이 일정에서의 도착·체류(시작~끝, 분), 이전 장소에서 도보(m·분), 가격, **장소 점수 Q와 세 구성요소 막대**(고유성 0.4 · 평판 0.3 · 시간대 0.3, 각 0~1과 근거: 지점 수, 평점·리뷰 수, 혼잡 1~4), **이 장소가 채운 말**(그 일정의 checklist 중 이 장소의 category/tags가 match된 항목: "지민 · 전시 · '전시는 꼭 보고 싶어'"), 숨은 한 곳이면 story·credit, 마이리얼트립 상품이면 평점·리뷰·시작 시각·[마이리얼트립에서 보기] 링크(새 탭), 지도 좌표 작은 글씨 + 데이터 출처 알약(`샘플` / `마이리얼트립 실조회` / `서울미래유산`; `source:"tmap"`이어도 실제 조회가 아니므로 "샘플"로 표기).
- 필요한 원값(지점 수 branches, 평점 rating, 리뷰 수 reviews, 혼잡 crowd 1~4, 영업 open/close)이 places JSON에 없으면 `solver/demo_builder.py`의 장소 직렬화에 `facts` 필드로 추가하고 `export_demo.py`로 `web/demo_data.js` 재생성. "이 장소가 채운 말"의 match 판정은 서버에서 계산해 stop에 `fills: [{person,label,quote}]`로 넣는 편이 낫다(`tripfit_solver.affinity` 재사용). `/api/try` 응답(06)에도 같은 필드가 실리는지 확인.
- 시트 열림·닫힘은 기존 스프링, 모바일(`body.mobile`)에서 손가락으로 닫기 가능.

## 4. TripFit 로고

사용자가 디자인·애니메이션은 아주 마음에 들어 하고, **로고만 어딘가에 들어가면 된다**고 했다. 기존 문법을 그대로 쓴 로고를 만든다.
- 마크: 4단계 합의 화면의 벤 다이어그램 문법 — 겹친 원 두 개(지민 핑크 `#FFCCE5`, 서연 하늘 `#8EC5EE`, navy 테두리), 교집합은 라임 `#D6F23B`에 체크. 0단계의 작은 "TripFit" 칩이 이미 비슷한 마크를 쓰고 있으면 그것과 같은 모양으로 통일.
- 워드마크: "TripFit" Inter Tight 600, 자간 -0.04em, navy.
- `web/logo.svg`(마크+워드마크)와 `web/favicon.svg`(마크만) 파일로 만들고 `<link rel="icon" href="favicon.svg">`(지금 favicon 404가 사라져야 함).
- 배치: 데스크톱 발표 화면 왼쪽 캡션 위(`01 / 06` 위, 높이 28px 정도), 앱 0단계 상단(현재 제목 블록이나 TripFit 칩 자리 — 화면을 복잡하게 만들지 말 것), 모바일 모드 0단계 상단. 다른 단계에는 넣지 마라.
- 첫 진입 때 마크의 두 원이 양옆에서 다가와 겹치고 교집합에 체크가 그려지는 짧은 스프링 애니메이션(0.8초 이내, reduced-motion이면 생략).

## 5. 3단계 체험 시트(마이리얼트립 상품) 디자인 다듬기

사용자가 이 시트의 디자인을 콕 집어 고치자고 했다. 지금 문제(스크린샷 기준):
- "마이리얼트립에서 보기 ↗"가 **브라우저 기본 파란 밑줄 링크**로 나온다 → 시트 안의 흰 알약 버튼(아이콘 `arrow`, 기존 `.pill` 문법, 새 탭)으로. 시트 하단 오른쪽 정렬.
- 별 **이모지(⭐)** → 기존 `svg()` 아이콘 문법의 별(또는 "평점 5.0 · 리뷰 16")로. 이모지 금지.
- "35,000" 대비 "원부터 / 1인 · 120분"이 기준선에 붙어 비좁다 → 숫자는 그대로 크게, 단위는 "원 / 1인"만 숫자 옆, "120분"은 아래 정보 줄로.
- "추정" 알약이 평점 옆에 있어 평점이 추정인 것처럼 읽힌다 → 추정인 값(소요시간 120분, 집결지 좌표) 바로 옆으로 옮긴다. 평점·가격·시작 시각은 실조회 값이라는 작은 표기("마이리얼트립 실조회 · 12:46").
- 집결지·소요시간·옵션 목록이 보라 위 **흐린 회색 글씨**라 거의 안 읽힌다(대비 부족) → 흰색 계열 대비 4.5:1 이상. 옵션 4개(10:00·12:30·15:00·19:00)는 텍스트 목록 대신 **작은 시각 칩 4개 한 줄**: 시간창(13:00–18:30)에 들어가는 것은 진하게, 밖은 흐리게+작은 "시간창 밖", 매진은 취소선. "조회 시 2인 예약 가능 · 35,000원"을 줄마다 반복하지 말고 한 번만.
- 아래 시작 시각 카드가 반 폭만 쓰고 "가능"이 줄바꿈된다 → 넣을 수 있는 시각이 1개면 전체 폭 카드(왼쪽 큰 15:00, 오른쪽 "120분 · 17:00 종료"), 2개면 반반. 문구 줄바꿈 없이.
- 시트 상단 여백·제목 크기·블록 간격을 다른 시트(시간 시트, 결제 블록)와 맞춘다. 벤토 블록 문법(라운드, 노치) 유지, 새 색 금지.
- 모바일(390px)에서도 같은 개선이 적용되는지 스크린샷.

## 6. 양보안 추천 + "이번엔 누구 차례" 양보 장부

3단계 "숲체험을 넣으려면 하나를 양보해야 해요" 화면은 지금 양보안 버튼 두 개(지민의 '전시 1곳' / 서연의 '카페 1곳')를 나란히 보여 주기만 한다. 사용자 요청: **둘 중 무엇을 양보하면 좋을지 추천**하고, **지난번에 누가 양보했으니 이번엔 누구 차례**라는 기억을 활용.
- **서버(`solver/demo_builder.py`, what-if 불가능 경로)**: 양보안마다 적용 결과를 미리 계산해 `relaxations[].preview = {sat:{지민,서연}, walkM, dropped:[이름], minSat}`. 추천 `recommended = {id, reasons:[...]}`: 1순위 근거는 공정성(양보 후 두 사람 중 낮은 쪽 만족도가 더 높은 안 = max-min), 2순위는 양보 장부(아래). 현재 데이터 기준 서연 카페 양보 58.8/59.7, 지민 전시 양보 20.6/78.7 → 서연 추천. `/api/what-if` 응답과 `whatif`(demo_data.js)에 모두 실어라. 06의 세션(`sessionId`) 경로에서도 동작.
- **양보 장부(기억)**: `D.history` = 지난 여행 기록(샘플, 화면에 "샘플" 표기): `[{date:"10.12", place:"익선동", person:"지민", label:"덜 걷기", note:"서연 따라 많이 걸음"}]`. 여기에 이번 세션에서 생긴 양보(2단계 "이 말은 양보할게" 토글, 3단계 선택)를 더해 사람별 양보 횟수를 센다. 프론트는 `localStorage`(try/catch, 없으면 메모리)에 이번 세션 기록을 저장하고 `R`(처음부터)로 초기화.
  - 추천 이유 문장 예: "지난번 익선동에선 지민이 양보했어요 · 이번엔 서연 차례" + "양보 후 59 : 60으로 더 고르게". 장부와 공정성이 서로 다른 안을 가리키면 공정성을 추천하고 장부는 "참고"로만 표시.
- **화면(3단계 양보안 블록)**:
  - 추천 안을 위에, 라임 테두리 + "추천" 알약 + 이유 두 줄. 다른 안은 아래에 덜 강조.
  - 각 버튼 안에 양보 후 결과 미리보기: 두 사람 만족도 작은 숫자(지민 59 · 서연 60), 빠지는 곳 수, 도보.
  - 블록 위 작은 "양보 장부" 줄: 사람 색 점과 누적 횟수(지민 1 · 서연 0), 탭하면 기록 목록 시트.
  - 자동재생(`_run`)은 추천 이유가 보이도록 1초 머문 뒤 추천 안을 고른다.
  - 4단계 합의 화면에 "이번 양보: 서연 '카페 1곳' → 다음엔 지민 차례" 한 줄(장부가 이어짐을 보여 줌).
- 엔진 로그: `MIP 양보안 2개 사전 계산 · 추천 category_min:cafe (min 58.8 vs 20.6) · 장부 지민 1/서연 0`.
- 테스트: 불가능 what-if 응답에 `preview`와 `recommended`가 있고, 추천이 max-min 기준과 일치.
